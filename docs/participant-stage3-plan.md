# Этап 3: переход от пользователя к месту за столом

Разделы до 3B фиксируют исходное состояние после `a700a47` (26.10.2026) и
историю перехода. Этап 3A завершён в проде (`bca598b`); бот-места и серверные
ходы остаются планом 3B и в рабочую БД ещё не включены.

## Текущее состояние

- У `room_players.id` есть `NOT NULL` и уникальный индекс
  `room_players_participant_id_idx`, но первичный ключ всё ещё
  `(room_id, user_id)`. Шесть ссылок на `room_players.id` заполнены,
  проверены внешними ключами и поддерживаются триггером dual-write
  (`participant-seats-expand.sql`, `participant-references-expand.sql`).
- `auth.uid()` остаётся идентичностью человека для авторизации. Игровая
  идентичность должна стать `room_players.id`; `rooms.host_id` может оставаться
  ссылкой на человека, пока бот не может быть хостом.
- В живой схеме голосование — прямой `INSERT` клиента в `votes`, а не `cast_vote`.
  Безопасная выдача карт — `get_luminaria_voting_cards`, а не
  `get_voting_submissions`. Её текущий результат `(id, card_id, player_id)`
  нельзя менять без учёта старых вкладок.
- Доступ к `room_players` у `authenticated` выдан по отдельным столбцам,
  пока без `id`. Проверка живых `column_privileges` показала, что
  `rooms.current_storyteller_participant_id`,
  `rounds.storyteller_participant_id`, `card_submissions.participant_id`
  и `votes.voter_participant_id` уже доступны для `SELECT`. Новые
  `INSERT`-гранты клиенту пока не нужны: старые записи заполняет dual-write.
  `room_deck_cards` имеет RLS, но прямое чтение клиенту отозвано: рука
  выдаётся через `luminaria_hand`.
- В живой БД `start_luminaria_game` всё ещё ограничивает стол семью людьми
  и требует два полных цикла, хотя клиент разрешает до 10 мест и один цикл
  начиная с семи игроков (`src/round-options.mjs`). Исправление включено в
  черновик перевода раздачи.

человека, а не обозначают игровое место.

## 3A. Сначала человеческие места, затем смена ключей

1. **Расширить контракт без изменения поведения.** Выдать `SELECT(id)` для
   `room_players`, подготовить совместимые RPC/выборки с ID места. Для
   `get_luminaria_voting_cards` сохранить старую сигнатуру и маскировку
   `player_id`; если нужен новый результат, создать версионированную функцию.
   В новом результате во время голосования нельзя отдавать чужой
   `participant_id`: его можно сразу сопоставить с публичным составом
   комнаты. Проверить, что опубликованные поля не раскрывают владельца
   чужой карты до итогов.
2. **Перевести клиентские чтения.** Получать `seat.id`, находить своё место
   через `seat.user_id = auth.uid()`, сопоставлять ведущего, подачи, голоса,
   очки и карточку лучшего раунда по ID места. Человеческие записи пока
   могут передавать legacy ID: dual-write заполнит ссылку на место.
3. **Перевести серверную логику.** Обновить действующие определения функций,
   триггеров и политик: очередь, guard, раздачу, руку, подачу, переход фаз,
   таймаут, голос, очки, обмен и реконнект. Не применять старые SQL-файлы
   поодиночке: последние определения разбросаны по миграциям. Для человека
   `auth.uid()` служит только для поиска его места и проверки полномочий.
4. **Переключить ограничения.** После аудита существующих строк добавить
   уникальность по новым ID. В отдельной короткой транзакции сменить PK
   `room_players` на `id`, сохранив `UNIQUE(room_id,user_id)`, и ключ
   `luminaria_card_rerolls`. Проверить зависимости шести внешних ключей от
   уникального индекса на `id` при репетиции с `ROLLBACK`. Старые
   `NOT NULL` можно ослабить только после готовности функций/триггеров;
   до 3B все места остаются человеческими. Поля `is_bot`, `bot_name`,
   `bot_avatar` можно добавить здесь с безопасными значениями по умолчанию,
   но вставка бот-мест должна оставаться закрытой.
5. **Раскатка.** Сначала совместимое расширение БД, затем клиент, затем
   ограничительный cutover. Открытые старые вкладки должны продолжать
   создавать раунд, подавать карту и голосовать. До появления ботов сверить
   результаты двух клиентов на комнате людей.

## 3B. Бот-места и серверные действия

Первый выпуск должен поддерживать **одного человека плюс двух ботов**:
человек может сразу сыграть полную партию и отгадывать карты ботов. Очередь
ведущих остаётся общей для всех мест, упорядоченных по `joined_at, id`.
Бот-ведущий выбирает карту из первых шести несыгранных карт своей руки и
загадывает короткую ассоциацию. Генерация моделью происходит вне транзакции;
если она недоступна, сервер использует проверенный локальный пул ассоциаций.
На этапе расширения схемы RPC добавления бота не следует открывать клиенту
до готовности серверных ходов, клиента и барьера для старых вкладок; иначе
хост сможет запустить зависающую бот-партию.

- Добавить `is_bot`, `bot_name`, `bot_avatar` и CHECK: у человека есть
  `user_id`, у бота его нет и есть имя. `user_id` станет nullable после
  смены PK. Старые поля действий (`storyteller_id`, `player_id`, `voter_id`,
  `owner_id`, `luminaria_card_rerolls.player_id`) тоже станут nullable;
  соответствующие ссылки на места обязательны, кроме свободной карты колоды
  и отсутствующего текущего ведущего. Уникальность по ID места обязательна.
- Хост управляет ботами в лобби через отдельные RPC. Проверять хоста,
  статус комнаты, лимит 10 мест, число настоящих игроков и допустимые имена.
- `luminaria_next_storyteller_seat` не фильтрует ботов. Guard создания раунда
  принимает бот-место только при `storyteller_id IS NULL`, если оно совпадает
  с `rooms.current_storyteller_participant_id`; человеческий legacy INSERT
  продолжает работать. RLS по-прежнему запрещает браузеру создавать раунд
  от имени бота.
- Ходы выполняет серверный оркестратор через закрытые идемпотентные RPC.
  Под блокировкой проверить комнату, фазу, бот-место, отсутствие повторного
  действия, владение картой в первых шести и допустимую цель голоса.
  Сервисный ключ не попадает в браузер. Сетевой вызов модели делать вне
  транзакции; при ошибке использовать детерминированный запасной выбор.
- RPC хода бота-ведущего атомарно проверяет текущую очередь и фазу, выбирает
  допустимую карту, отмечает её сыгранной, создаёт раунд и сразу записывает
  подачу ведущего. Повторный вызов для того же хода ничего не удваивает.
  Сам текст ассоциации должен проходить действующий лимит `rounds.clue`;
  fallback хранится на сервере и не требует внешней модели.
- Отображать бота из `bot_name`/`bot_avatar`; не запрашивать `profiles` по
  `NULL`. Бейдж и политика звёздочек должны быть явными. До поддержки
  старых открытых вкладок для бот-комнат нужна проверка версии клиента либо
  иной барьер, иначе старый UI склеит всех ботов по ключу `null`.

## Минимальная проверка перед применением

На тестовой копии схемы или в транзакции с `ROLLBACK`: нулевые сиротские
ссылки, сохранение seat ID после `reclaim_luminaria_seat`, PK/FK и
уникальность, переход 3 человеческих игроков через старт → подача → голос →
итоги → следующий ход, старый и новый клиент, отказ от повторного голоса
и от чужой карты. До 3B отдельно проверить бот-сценарий и доступность
только разрешённых строк/полей под ролью `authenticated`.

Локальный черновик первой половины 3A разбит на четыре SQL-файла в порядке
применения: `participant-contract-3a.sql`, `participant-gameplay-3a.sql`,
`participant-actions-3a.sql`, `participant-deal-3a.sql`. Они не меняют PK,
не снимают `NOT NULL`, не меняют RLS и не включают ботов. Перевод политик
RLS на ID места, новый контракт клиента и смена ключей остаются следующей
частью 3A. На 26.10.2026 все определения
прошли синтаксический прогон с `ROLLBACK` в живой схеме; совместно проверены
старое и новое направление dual-write, очередь, ожидание, рука и статус
обмена на завершённой комнате из трёх человек. В отдельных транзакциях с
`ROLLBACK` проверены финализация исторического раунда с полным набором
голосов, пропуск истёкшего хода ведущего и автоподача отсутствующей карты
с автоматическим переходом в голосование. Единый откатный прогон
`tests/participant-3a-rollback.sql` затем проверил раздачу 100 карт на
10 мест (по 10 карт, позиции 1–10, оба ID владельца), руку из первых
6 карт, обмен с повторным вызовом и старую вкладку: `INSERT rounds`
с `storyteller_id`/`clue`, `play_luminaria_card` и прямой `INSERT votes`
без полей места. Обнаружено и исправлено действующее ограничение
`rooms_round_cycles_check`, которое запрещало один круг при 7–10 игроках.
После отката подтверждены прежнее ограничение `round_cycles >= 2`,
отсутствие тестовых раундов/обменов и отсутствие нового гранта в живой БД.

26.10.2026 четыре модуля применены к рабочей Supabase в указанном порядке
одной транзакцией с `NOTIFY pgrst, 'reload schema'`. Контрольный запрос
подтвердил `SELECT(room_players.id)` для `authenticated`, доступность
остальных новых колонок, `round_cycles >= 1` и определения функций раздачи
и голосования с `participant_id`. Действующий сайт после миграции загрузил
главную и список открытых комнат без ошибки. Клиентский переход 3A.2
выполняется отдельно; RLS и первичные/уникальные ключи ещё не переключены.
Серверный коммит `00d17cc` опубликован в `origin/main` после применения SQL.
Клиент 3A.2 читает `room_players.id`, находит своё место по `user_id`,
сопоставляет ведущего, итоги и карточку лучшего раунда по ID места с
фоллбэком для старых строк. Фаза голосования продолжает определять свою
карту по маскированному `player_id` из `get_luminaria_voting_cards`.

Это сохраняет **текущую** математику партии: на 10 игроков один круг
содержит 10 раундов и раздаёт 100 карт. После пяти сыгранных карт
шестёрка руки начинает уменьшаться, но оставшихся карт хватает на каждый
из 10 ходов. Если требуется ровно шесть вариантов на каждом ходе,
понадобятся 15 карт на человека (150 на стол) плюс резерв обмена;
четыре колоды сейчас содержат только по 110 карт. Такой пересмотр
размера раздачи потребует отдельно отвязать лимит раундов от максимальной
позиции карты и не входит в совместимый перевод ID мест.

27.10.2026 подготовлены `participant-keys-3a.sql` и
`participant-rls-3a.sql` для завершения 3A. Первый сохраняет старые

делает обязательные ссылки `NOT NULL` и добавляет уникальность игровых
действий по месту. Второй переводит RLS создания/обновления раунда,
голосования и чтения скрытых подач/голосов на ID места, сохраняя запрет
прямой подачи карты. Откатный сценарий
`tests/participant-final-3a-rollback.sql` вместе с обоими модулями
вернул `Stage 3A keys and RLS passed; rollback follows` в рабочей схеме.
Затем оба исходных файла применены отдельно к рабочей Supabase.
Контрольный запрос подтвердил PK места и обмена по ID места, все шесть
FK, старую уникальную пару для совместимости, три новых уникальных
индекса, одну политику голосования по ID места и одну политику чтения
подач. Это завершает человеческий этап 3A; бот-места остаются этапом 3B.
